Architecture · Linux · PREEMPT_RT · x86_64

jack2dbus-nspa

JACK2 1.9.22 — the release Arch Linux ships — with a set of real-time, correctness and performance changes to the server engine, the ALSA driver, jackdbus and libjack's internals. It installs as one package in place of Arch's jack2 + jack2-dbus: same files, same paths, same configure options, LTO enabled.

The constraint behind every change: no client API/ABI change and no wire-protocol change. The shared-memory layout, the futex protocol, the request encoding and the time base are exactly 1.9.22's, so an application carrying a stock libjack (64- or 32-bit) works against this server, and this libjack works against a stock server. The one addition is optional — a small side file in which each client's realtime thread holds a robust mutex, so the server learns the moment it ends (§12) — and either side does without it when the other lacks it. Everything here happens behind those interfaces — on the RT driver thread, in the engine's per-cycle work, in the server's control threads, in libjack's own locking — and every change was measured on the engine itself, not on a microbenchmark.

1System overview

Separate client processes, one server process, and the shared memory in /dev/shm between them. Audio never crosses a socket: port buffers live in the graph segment and are read and written in place. Futex words wake each client when its inputs are ready; sockets carry only requests and notifications.

audio samples (mmap, port buffers) activation (futex wake) requests (socket) notifications (socket) MIDI (ALSA sequencer) D-Bus alive slot (robust futex → futex_waitv) upstream layout / code, unchanged changed in the fork operating system

Three planes. The data plane is shared memory: the driver converts the card's mmap area into port buffers in jack-1000-0, clients read their inputs and write their outputs there directly, and an input connected to one output gets that output's buffer pointer (zero-copy). The activation plane is one futex word per client: a client runs when the activation counter for its inputs reaches zero and its futex is signalled. The control plane is two kinds of socket — requests from libjack to the request thread, notifications back to each client's notification thread — plus D-Bus for jack_control and the device reservation PipeWire honours.

What the fork moved. Everything in the amber column is protocol 9 and stays byte-identical, so a stock libjack in any process (a bundled one, Arch's lib32-jack2) still attaches. The changes live in the violet boxes: the RT driver thread no longer issues socket writes or condvar signals (the two bounded queues and the futex event count), the engine's per-cycle loops stop at the highest live refnum, and libjack serializes and snapshots what it used to race on. Since the first edition the server also learns at once when a client's realtime thread ends: the dashed violet box is the fork's one addition to /dev/shm, optional on both sides, and the rose line is the kernel waking the notifier through it (§12).

2Processes and threads

JACK2 runs its engine and its hardware driver inside one server process — jackd on the command line or jackdbus as a D-Bus service; both link the same libjackserver — and every application is a separate process linked against libjack. Exactly one thread on each side is real-time: the server's driver thread, and each client's process thread.

jackdbus · the server

D-Bus service org.jackaudio.service, started on demand by the session bus; embeds the JACK server. jack_control, qjackctl and Cadence talk to it.

  • Main thread. The D-Bus loop: engine and driver parameters (persisted in ~/.config/jack/conf.xml), start/stop, the patchbay interface. Fork: SIGTERM/INT/HUP are consumed and end the process cleanly (C11); the crash handler only writes and re-raises (C17); control operations are serialized with the request thread (C20); a failed master switch can't wedge it (C19).
  • Request thread. Polls the request socket and every client socket; client open/close, activate, connect, port registration. Takes the engine lock — never the RT thread. Fork: also removes clients whose process died (§12), and queues notifications for a client that falls behind instead of waiting on it (§14).
  • ALSA driver thread, SCHED_FIFO 89. Waits on the PCM, converts samples, runs the engine's per-cycle step and wakes the first clients. Fork: no syscalls besides poll and activation futexes; memory locked (R1); per-cycle loops bounded (§5).
  • Engine notifier and message buffer threads. New in the fork. They drain the RT thread's lock-free queues every 20 ms and 50 ms and do the socket writes and log I/O the RT thread used to do (§6). The notifier's wait is a futex_waitv on its own wake word and the alive slot of every active client, so a client's realtime thread ending wakes it within microseconds (§12).
  • alsa_seqmidi port thread (-X seq). Subscribes and unsubscribes sequencer ports as they appear and hands them to the RT side through bounded rings (C22).

3Shared memory and the wire protocol

The server creates the shared objects; clients map them by name. Their layouts, together with the futex-word protocol and the request encoding, are what protocol 9 freezes. The fork never changes a byte of them.

Why the layout is frozen. The server and every libjack compute addresses in these segments independently: a port buffer's zero-copy address, a client's activation counter, the frame timer a client reads in jack_frame_time(). A single moved field reads as garbage in a client built from another tree — which is what upstream's develop did to JackEngineControl (C2), and why the fork is based on the 1.9.22 tag rather than on develop.

Everything that grows or tracks state lives outside. The refnum high-water mark, the RT queues, the notifier and message threads, the dirty-row bookkeeping and the PM QoS file descriptor are all in the server's private heap. The only shared-memory behaviour that changed is who writes when: fewer writes per cycle (bounded resets), smaller copies per graph edit. The one new shared object, the alive-slot file, is separate from all of these and optional on both sides (§12).

4The process cycle

One period of 512 frames at 48 kHz, 10.67 ms, in asynchronous mode (the default). The driver thread wakes on the card's period interrupt, moves samples, runs the engine's per-cycle step and wakes the clients with no upstream dependency; from there the clients wake each other. Not to scale: the driver's share is tens of microseconds.

Async vs sync. In the default asynchronous mode the driver writes the previous cycle's output, wakes the graph and goes straight back to poll(); a late client costs that client's output, not the driver's schedule. With -S (sync) the driver waits for the graph's end node with a timeout and writes the current output — one period less latency, but a stuck client stalls everyone (measured in §20). The engine decides at each cycle start whether the previous graph finished (IsFinishedGraph); if it didn't within the client timeout, it switches state anyway and reports an xrun.

What the fork changed on this path. Read fills a capture port in the cycle its connection takes effect (C24). CycleBegin and RunNextGraph touch only live refnums, and ResumeRefNum skips empty successor slots 16 at a time (§5). The graph-order notification is a TryPush into a bounded queue instead of a socket write() (§6); the "cycle passed" event for waiting control threads is one atomic increment instead of a condvar signal. Sample conversion runs without libm calls (P2/P3). After an xrun the frame timer is re-seeded instead of running backwards (C6), and recovery restarts only the PCM streams (R2).

5Activation graph and per-cycle loops

JACK2 runs clients in parallel wherever the graph allows. Each client has an activation counter in shared memory, reset every cycle to its number of predecessors; every predecessor that finishes decrements it, and the one that takes it to zero signals the client's futex. No central scheduler runs during the cycle.

Start and end node. The freewheel driver (refnum 1) runs as a slave of the ALSA driver in normal operation. At activation every client is connected from it and to it (DirectConnect(1, ref) and DirectConnect(ref, 1)), so each cycle it signals every active client, and every client signals it when done. IsFinishedGraph() is simply "refnum 1's counter reached zero". A client with inputs from the driver and from other clients waits for all of them: its counter counts predecessors, not ports (fConnectionRef holds the port count per client pair; the counter moves only on the first and last port connection between two clients).

Where the per-cycle time went. A perf profile of the server (16 clients, 32-frame periods) put about 40% of its user-space time in three loops over all 256 client slots: ResetGraph (activation counters and timings — shared-memory lines the clients' cores wrote last cycle, so each store is a cross-core transfer), ResumeRefNum (the successor scan, also the top hotspot in every client) and CalcCPULoad. Refnums are allocated lowest-first, so live clients are always at the bottom of the table: the server keeps 1 + highest refnum in use (release store when the table changes, acquire load per cycle) and its loops stop there. The successor scan, which runs in every libjack, reads 32 bytes at a time and only looks at individual entries in a non-zero chunk, in the original order.

6RT side channels without syscalls

Besides waking clients, the driver thread has three things to tell the rest of the server: notifications (graph order, xruns) for the clients, "a cycle has passed" for control threads waiting on a graph change, and log messages. In 1.9.22 each of those is a kernel entry from a SCHED_FIFO thread — and on PREEMPT_RT every kernel wake path takes a sleeping, priority-inheriting lock.

The queue. JackBoundedQueue is a bounded multi-producer/multi-consumer ring with a sequence number per cell (Vyukov's design): a producer claims a slot with one compare-and-swap on the enqueue position and publishes it with a release store of the cell's sequence; head and tail positions sit on separate 64-byte lines. A full queue is not an error path that blocks — the item is dropped and counted, and the count is reported when the server stops (the notifier's 20 ms wait has since become a futex_waitv that also watches the clients' alive slots, §12). Notifications are asynchronous by contract (graph order, xrun callbacks), so up to 20 ms of added delivery delay is invisible; ordering and the threads that run the callbacks are unchanged.

The cycle signal. Control threads (client activate, deactivate, close) wait for "a cycle has passed" so that a graph change is known to be in effect. JackCycleSignal is a futex event count: the RT side increments a generation counter and calls FUTEX_WAKE only if a waiter flag is set — almost never; waiters sleep on the generation with a CLOCK_MONOTONIC timeout. The glibc condvar it replaces took its internal lock on every signal, every cycle, from the RT thread. Logging still formats the message on the thread that logs, but no longer locks or wakes anything; MIDI drops are logged once per burst rather than per event (R8), and the ALSA adapter's RT thread now uses the threaded log function (R6).

7Graph changes: the double-buffered state

The connection state is double-buffered so the RT thread never takes a lock to read it. Writers (the request thread) edit the next state; the RT thread adopts it at a cycle boundary with one atomic operation; readers re-check a counter to detect a switch under them. The cost sits entirely on the writer — which is where 1.9.22 spent 19 MB per edit.

19 MB per edit. With Arch's build options (--clients=256 --ports-per-application=2048) one JackConnectionManager is 19.05 MB. 1.9.22's WriteNextStateStartAux copied all of it into the next state at the start of every write session after a switch: about 38 MB of memory traffic per connect or disconnect, streamed through the last-level cache the RT threads share. While patching at small periods that's gigabytes per second of cache pollution. The fork copies only the used part of each table: the JackFixedArray invariant keeps items compact in [0, count) with EMPTY after them, so the copy stops at the count. A unit test compares the result byte for byte with a full copy (300 rounds, the full 19 MB state).

Waiting for a change. Some API calls (jack_port_connected, the latency queries) sleep up to 1.1 periods if a change is pending, so a caller sees the graph it just requested — except on RT threads, which must never sleep. Threads created with jack_client_create_thread weren't recognised as RT and slept too: 2945 µs measured in a 2667 µs period. The fork marks them like the process thread (R10), and tests for a pending change before reading the thread marker, so the common case reads no thread-local state at all.

8The ALSA driver

jack_alsa.so owns the card. It maps the PCM's ring buffer, waits for each period with poll(), converts between the card's integer format and JACK's 32-bit float port buffers, and drives the engine's cycle. On this machine: Intel HDA, Realtek ALC274 (24 significant bits in S32_LE), 48 kHz, 512 × 2.

Why the stale buffer. To save work the driver converts only capture channels that have a connection. It asks the graph before the engine's switch (Read() runs first in the cycle), so in the cycle a new connection takes effect the port is skipped — and its buffer still holds whatever was converted the last time it was connected, possibly minutes ago. The client hears a period of old audio. The fork converts every channel while a graph change is pending (IsCaptureChannelNeeded) and zeroes a skipped buffer once when a port stops being connected (SkipCaptureChannel), so the worst case is a period of silence, never old audio. The same logic covers the FireWire driver.

Around the cycle. The poll timeout was computed in microseconds and passed to poll() as milliseconds: 16 s at 512 frames, so a stalled device took that long to be noticed, and stop or buffer-size changes could block as long (C8). An xrun ran the full JackDriver::Stop/Start on the RT thread, restarting slave drivers with thread joins and allocations; the fork drops, prepares and restarts only the PCM streams, with the descriptor array allocated once (R2). A fatal device error now reaches clients as a shutdown notification instead of a silently dead driver thread (C13). After any xrun the frame-timer DLL is re-seeded, so jack_frame_time() doesn't run backwards for a period and take a second to reconverge (C6).

9MIDI through -X seq

With -X seq the ALSA driver bridges the ALSA sequencer: every sequencer port becomes a JACK MIDI port (system:midi_capture_N / system:midi_playback_N). A non-RT port thread follows ports as they come and go; the RT thread moves the events each cycle, placing them by the sequencer's timestamps.

The asserts (C22). The hand-over rings between the port thread and the RT side held about 63 ports per direction, and overflow was an assert: 150 sequencer ports at startup, or a burst of new ports while running, aborted the whole server. The fork drops and counts instead — a port that didn't fit is picked up again on the next announcement — and the hash race between the two threads is closed. On hw:PCH, 1.9.22 aborted in update_port_type with 150 ports at startup and in port_event on a 150-port burst (4 of 5 runs); the fork started with 152 MIDI ports and survived every burst.

The idle ioctls (P5). Each cycle, read and write both fetched the sequencer queue's real time with snd_seq_get_queue_status() — an ioctl that takes the queue's lock, an rt_mutex on PREEMPT_RT — whether or not any MIDI was flowing. The time is only needed to place an event, so it is now sampled, together with JACK's frame time, the first time an event needs it in that cycle. Because both clocks are sampled together as before, a later sample shifts both alike and every event lands on the same frame: the loopback test shows identical latency distributions.

10libjack: the client side

libjack is code running inside every JACK application. Its API and ABI are fixed, but its internals — how it serializes requests, publishes callbacks, keeps per-thread state and shuts its threads down — are free to change, and that is where the client-side races were.

Requests and activation. All of a client's API calls share one request socket. 1.9.22 wrote a request and read its reply without a lock, so two application threads calling at once could read each other's replies and desynchronize the stream for good: 1 599 errors and a hang in the concurrency test, 0 now (C9). jack_activate returned before the process thread had run its buffer-size and thread-init callbacks, so a slow callback made the first cycles late: 13 xruns per activation with a 60 ms callback, 0 now (C10).

Cancellation at close. jack_client_close stops the client's threads with asynchronous cancellation — a cancel can land on any instruction, inside malloc or inside a lock. Switching to deferred cancellation (R9) was rejected: a callback blocked on an application lock would turn into a permanent hang. The fork instead disables cancellation around its own locks (JackNoCancelScope); a cancel that arrives inside is acted on when the scope ends. glibc does that inside pthread_setcancelstate(), i.e. in the scope's destructor, and a C++11 destructor is noexcept: the first version aborted the application. Found by the sanitizer runs; the destructor is now noexcept(false) and a unit test cancels 100 threads inside the scope (aborted on the first before, 100/100 clean after, 64- and 32-bit).

Per-thread state. The RT marker, the notification-thread marker and the per-thread log function were pthread keys. They are now __thread pointers, and x86 builds use -mtls-dialect=gnu2: with TLS descriptors a read is an indirect call to glibc's two-instruction static-TLS resolver, and glibc places a dlopen()ed libjack in surplus static TLS (checked: all three descriptors resolve to _dl_tlsdesc_return). The default dialect would have been slower than the pthread key (3.2–3.5 vs 2.9–3.1 ns) and can allocate through __tls_get_addr after a later dlopen. Initial-exec TLS isn't an option: libjack is dlopen()ed by weakjack users and Wine.

11jackdbus, PipeWire and the card

jackdbus is the JACK server packaged as a D-Bus service: the session bus starts it on the first call to org.jackaudio.service, it keeps its settings in ~/.config/jack/conf.xml, and it owns the card through the desktop's device-reservation protocol. On this system PipeWire runs on top of it as an ordinary JACK client, carrying the PulseAudio and ALSA applications.

The hand-over. Card ownership is negotiated on the session bus (org.freedesktop.ReserveDevice1.Audio0): JACK requests the name with the highest priority and PipeWire gives it up. The reverse is automatic — when JACK lets go, WirePlumber acquires the card for its own ALSA node and re-applies its stored route volumes. Two practical consequences surfaced during this work: a JACK start right after PipeWire took the card can find the PCM still open for a moment ("device busy", a retry starts it; stock 1.9.22 behaves the same), and anything muted on the card while JACK was stopped gets un-muted by WirePlumber, which the hardware test harness now guards against (§18).

Engine parameters through D-Bus. Everything settable on jackd's command line is an engine or driver parameter of the control API, so the fork's PM QoS option is available to jackdbus as well: jack_control eps cpu-dma-latency 0 holds a 0 µs request on /dev/cpu_dma_latency while the server runs and releases it when it stops (default off; worth it at 64–128 frames, not at 512).

For session managers and monitors. Four calls were added for tools around the server, all through libjackserver's control API (common/JackControlNspa.h), none in libjack. A session manager that is about to stop an application asks first, by client name or by the pid it started, and the application's clients leave the graph before the signal (§12). A monitor reads, per client, the cycles it ran late and its longest cycle (§13). An older jackdbus answers UnknownMethod, and a tool carries on as before.

12When a client dies

A client process can end at any moment — killed, crashed, closed by a session manager. Until the server takes it out of the graph, every cycle waits for it. 1.9.22 learned of a death only from the client's sockets closing, and the kernel closes a dying process's files after it has torn down its memory: for a large process, hundreds of milliseconds of stalled cycles. The fork learns it from a step the kernel takes first.

The kernel's order. do_exit() handles a thread's robust futexes at the very start of exit_mm(): futex_exit_release() walks the thread's robust list, and handle_futex_death() sets FUTEX_OWNER_DIED in each lock the thread held and wakes one waiter. Only then is the address space torn down, then the files closed (exit_files()), then the parent notified (exit_notify(), where a pidfd becomes readable). The robust-futex step happens whichever way the thread ends, and it is microseconds after the signal. (Checked in the Linux-NSPA 7.3.3 source.)

One step out. Taking a client out of the graph used to publish each disconnection separately, notify every client of each, and remove the client's activation edges last — every cycle until then waited for it. Now all of it goes into one write session of the double-buffered state (§7): the realtime thread switches to the whole change at once, and the switch is forced at the next cycle. The notifications follow, and none goes to the dead client itself: no broken-pipe errors, and its ports are announced gone once (1.9.22 announced them twice).

The alive slot. The server creates /dev/shm/jack_alive.<uid>_<server>, one 64-byte slot per client refnum. A fork libjack makes its client's slot a process-shared robust mutex — in its own glibc's layout, 64- or 32-bit, both of which begin with the futex word — and its realtime thread locks it when it starts and never unlocks it. The server only ever reads and CASes that first word (owner TID, FUTEX_WAITERS, FUTEX_OWNER_DIED): it sets FUTEX_WAITERS so that the kernel wakes it, and the notifier sleeps in futex_waitv on its own wake word and every watched slot at once. The file is the fork's one addition to /dev/shm, and optional on both sides: a stock libjack never opens it (its clients fall back to the next page), and a fork libjack facing a server without it does without.

/proc, for any libjack. When the graph does not finish, the realtime thread does one relaxed store and, at most every 100 ms, wakes the notifier, which asks the request thread to look. The request thread checks each unfinished client's process through /proc: the pid comes from SO_PEERCRED on the client's socket (the pid as the server sees it, across PID namespaces), the start time tells it from a later process with the same pid, and the entry's owner must be the client's uid. Exiting or gone: the client is taken out of the graph at once, and removed after the switch. A client found alive is left alone for 100 ms; the server never decides from timing that a living client should go.

The socket. 1.9.22's only signal remains the last resort. It arrives after the memory teardown, and not at all while another process holds the sockets: libjack doesn't set close-on-exec, so a child the client forked inherits them, and in the killfork test the graph stalled 4.7 s until the child went too. The slot, or /proc (which looks at the client's own process), finds the death first.

A session manager knows beforehand. No signal is earlier than being told: a session manager that started an application can ask jackdbus to take its clients out of the graph before it stops it. That works with any libjack inside the application, and even when the application is killed in the middle of its callback — the one case the slot can't help a stock libjack with. The calls are described with the rest of the D-Bus interface in §11.

13Late clients: catch up, report, count

A client that overruns its period is alive and busy: nothing to remove. The fork keeps how JACK lets a late client catch up, reports each failing cycle once and names the client behind it, and counts per client how often, and by how much, it ran late — without slowing a cycle in which nobody did.

Catch-up, kept. At the next cycle start the engine resets the graph and the late client's inputs trigger it again; when it finishes the late cycle it finds its futex already signalled and runs the next one straight away. After a one-off spike it has processed every block of its input; what was late is its output for one cycle. Making it skip its next trigger instead, as CoreAudio does with an overloaded client, would relieve it, but in a graph its late finish has already signalled its successors, and the skipped block of input is lost to it for good: a recorder gets a gap, an effect's state jumps, and a note-off in that block is a stuck note. That was designed, analysed, and dropped before a line of it shipped.

One xrun per failing cycle. 1.9.22 sent an xrun notification for every client it found unfinished, so a client that died or hung in the middle of a chain counted as several xruns, each with its own log line, and jack_get_xrun_delayed_usecs() kept returning whatever the driver measured last (698 s was seen). Now a failing cycle is one notification and one line naming up to four unfinished clients, with their state and how long since each was triggered, and the delay value is this xrun's: the longest time an unfinished client had been in its cycle.

Late cycles, for free. A late client means an unfinished graph: on a cycle that finished, nothing is counted and nothing is read. On a cycle that didn't — already the engine's slow path, where it reports the xrun — each client in the graph that was triggered and hadn't finished is counted. A client still waiting for one of its inputs isn't: the one it waits for is, so the count points at the slow client, not at what follows it.

Cycle lengths, on demand. How close each client runs to its deadline, even when nothing is late, needs every client's wake and finish times every cycle. That costs the realtime thread about 50 instructions per client, so it runs only within a minute of the last GetClientTimings call: a monitor that shows the numbers polls, and pays while it watches. A late cycle overwrites nothing until its catch-up does, so it is measured up to the client's next wake (exact in the usual back-to-back case), and while it lasts, up to now. In freewheel mode nothing is counted.

14Slow notification clients

Notifications reach each client's notification thread over its own socket, and some of them wait for a reply. In 1.9.22 the request thread waited for each of those under the engine lock: one client that answered slowly — a plug-in host busy in a callback, a debugger stop — held up every other client's open, connect and disconnect, and one that stopped reading blocked the server for good.

Lagging. A client lags when it doesn't answer a latency notification within 500 ms (each client gets two after every graph change, in graph order), or when its socket couldn't take one more notification without blocking. While it lags, its notifications are queued in order and sent as it catches up, from the request thread every 50 ms; the replies it still owes are counted and read as they come, so a late reply is never taken for a later one's. It receives every notification, in order, some of them late; only a client that doesn't read long enough to fill its queue (4 096) loses some, counted and reported, followed by a graph-order notification so it re-reads the graph.

Which waits remain. Buffer size, sample rate, freewheel, a new client's registration, activation and session notifications are still waited for as in 1.9.22, up to 2 s: the client has to have handled the change before the server goes on. A lagging client first gets the chance to catch up within that same time. Known edge, of the same kind as 1.9.22's after its timeout: a lagging client learns of new clients late, and a client connected after it can miss cycles until then.

One write per notification. A notification was eight write() calls, one per field; it is one now, with the same bytes on the wire. That also makes the "room in the socket" check exact: a notification is either written whole or queued whole.

15Failure modes fixed

Four failures that cross process boundaries, each reproduced against stock 1.9.22 before it was fixed. Step through them with the arrows.

C1 · found the hard way. During the audit a test server on the same machine unlinked the live jackdbus server's graph segment. All of a user's servers share one registry, and jack_destroy_shm() unlinked by registry index without checking who allocated the entry. The wrong index came from an object-lifetime bug that only LTO exposes: the segment info was written before placement-new started the object's lifetime, and GCC's lifetime dead-store elimination dropped the writes — the same root cause as upstream's long-open LTO crash (#485). Since then every test server runs in a private user/mount/IPC namespace with its own tmpfs on /dev/shm.

C25 · found on hardware. A client process that survives its server — hung, or ignoring the shutdown callback — keeps its futex file mapped. 1.9.22 left those files in /dev/shm when it stopped with clients connected, and the next server's Allocate() reopened an existing file instead of creating a fresh one. A new client with the same name then shares its futex word with the old process, which consumes every other wakeup. The first hardware run found it: an orphaned test client cost a 1.9.22 server 906 xruns in 20 s.

C6 · every xrun. After an xrun the driver resets the frame timer. 1.9.22 set the current wakeup but not the next, so for about a period Time2Frames ran backwards (or divided by zero) and the DLL needed about a second to settle. Clients that schedule by frame time — MIDI output, transport, anything using jack_frame_time() — saw time jump. The fork re-seeds the DLL and publishes a consistent state; libjack also guards against a non-positive period.

db5.3 · a packaging bug with runtime effects. The metadata store is a Berkeley DB environment in /dev/shm shared by the server and every client. A process linked against another Berkeley DB version can't open an environment created by the first one, and silently loses metadata. The fork's first build picked up the system's db 6.2; Arch links db5.3. The same messages appeared earlier in this work whenever a 1.9.22 client met a fork server — the test that now gates it fails 4/4 against a 6.2 build.

16Performance, measured in the engine

Every performance change was measured on the running engine — real clients, the same server, interleaved A/B runs, perf counters per cycle — and kept only if no configuration got slower. Hot-loop microbenchmarks were used to explore, never to decide: one change that won 2–3× in a hot loop lost 30–40% in the engine and was reverted.

Method. Server and client CPU per cycle come from perf stat on the processes (user space, instructions and cycles) divided by the cycles in the window; the critical path is what the last client of a chain records as finish time − cycle start, i.e. what DSP load measures. Variants run interleaved in balanced order (ABBA) against the same server build, in an isolated namespace, on one CPU model; where the result was noise-bound (C-state wake-ups at 2 clients), the run was repeated with a 0 µs PM QoS hold to separate code from power management.

17Compatibility envelope

"Drop-in" is tested, not assumed: every combination of server and libjack that can meet on a desktop runs the same stress client, and the cross-process state that isn't covered by protocol 9 (the metadata database) has its own cross-build test.

What makes this hold. The fork changed no shared layout, no futex semantics and no request encoding; the develop request rework it took writes the same fields in the same order (all 96 field reads compared), only as one complete packet. Everything new — the refnum bound, the queues, the dirty-row bookkeeping — lives in the server's private memory, and the client-side changes (request lock, snapshots, TLS, the chunked scan) only change how libjack's own threads coordinate. The package provides jack2=1.9.22, so packages that depend on it, Arch's lib32-jack2 included, stay installable.

The alive slot, cell by cell. Fork libjack on this server, 64- or 32-bit: a dying client is found through its slot (the 32-bit glibc's mutex starts with the same futex word). A stock libjack on this server never locks a slot and is found through /proc when the graph waits: one xrun per kill instead of hundreds, none if a session manager detaches it first. A fork libjack on a stock server finds no file and does without. Kernels without futex_waitv (before 5.16): the slots are polled every 20 ms.

18Validation harness

Tests never touch the live audio session. All of a user's JACK servers share one shm registry and its SysV lock, whatever their names — which is how an early test unlinked the live server's segment (C1) — so every test server runs in private namespaces; the hardware tests stop the session explicitly and restore it.

Why a watchdog. The first hardware run muted the card once at the start; one second after jack_control stop WirePlumber took the card and re-applied its own volumes, and the speakers were live for about 90 s of 64-frame tests until noticed. The harness now keeps a watchdog in its own session for the whole time JACK doesn't hold the card, checks the mute before and after every test server starts (with retries, aborting if it can't), restores in a safe order, and warns if WirePlumber persisted a muted route. NSPA_HW_MUTE_SELFTEST=1 exercises the watchdog alone with an inaudible S/PDIF switch.

Sanitizers, and what they can't run. Under TSan, libjack's asynchronous cancellation of a client's threads (at deactivate and close) aborts the instrumented client — a TSan limitation, documented in the suite — so TSan runs are gated on reports, not on client results; the jackdbus tests also run against a TSan server with uninstrumented clients, where all pass. The one report left is older than the fork's changes (§20).

20Open items

What was measured and deliberately left alone, what remains untested on hardware, and where larger gains would have to come from.

Not covered yet

Implemented without the hardware to prove it here, or still to be looked into.

  • Device removal (C13): a fatal device error reaching clients as a shutdown notification.
  • -X raw: non-blocking wake pipes are in (R3); drain and thread priority unchanged; one failing raw MIDI port still stops the I/O thread for all (C21, not done).
  • "Device busy" right after a PipeWire takeover: a short retry of the PCM open after acquiring the reservation would remove the race; optional, not done.
  • FireWire (FFADO): built like Arch's package, not tested; not used on this system.
  • A TSan report older than the fork's changes: JackMessageBuffer::AddMessage against jackdbus's log callback, around the message buffer's lifetime across StartServer/StopServer; the queue itself is clean under TSan. To investigate.
  • Xruns when apps start or add tracks. In real use they come from the app's own callback (Ardour busy for just over one period during a load), not from the server; in async mode the other clients' audio is untouched. Next: measure with GetClientTimings during app start, track adds and plug-in inserts.

Larger directions

Where further gains would come from, and what they cost.

  • A dual-protocol server. The client-open request already carries a protocol version. New libjack: memfd segments passed over the socket, sealed, optionally huge pages, sized to actual use instead of a fixed 107 MB; old libjack: today's named segments. No recompiling of applications — libjack is a drop-in — but full benefit only when every libjack in use is new.
  • The scheduler. What remains per cycle is wake-up latency and cache-line transfers: IRQ and CPU isolation, sched_ext policies, proxy execution — kernel and system work rather than JACK code.
  • An opt-in isolation mode. A client chosen by the user runs one cycle behind, with its outputs double-buffered by the server: its lateness can never hold up anyone else, at the start of a session or when it adds tracks (PipeWire's node.async). It costs that client one period of latency.
  • What a late client's output should sound like. Repeat, silence or a short fade (PipeWire plays silence, and fades on link removal): a matter of taste, parked.

21Packaging and deployment

nspa/pkg/jack2dbus-nspa/PKGBUILD builds one package from the repository's main branch (or a local clone with NSPA_REPO) that replaces Arch's jack2 and jack2-dbus.

jack2dbus-nspa

The same 62 files at the same paths as jack2 + jack2-dbus; docs and lib32 left out.

  • Version. pkgver() from git describe on the 1.9.22 tag, e.g. 1.9.22.r98.g3b031c4e: sorts after 1.9.22.
  • Provides. jack, jack2=1.9.22, jack2-dbus=1.9.22, libjack.so=0-64, libjacknet.so=0-64, libjackserver.so=0-64; every package depending on jack2 (Ardour, mpv, OBS, qjackctl, wineasio, lib32-jack2) stays satisfied.
  • Conflicts. jack, jack2, jack2-dbus.
  • Build. Arch's configure options (--classic --dbus --systemd-unit --autostart=none) without doxygen; makepkg's flags with LTO; Berkeley DB 5.3 found by the wscript, no patch.
  • Validated as packaged. The full suite against the extracted package's binaries (38/38 at r72); the jackdbus tests, detach and timings included, against r98: 14/14.

Installing on a running system

jackdbus is a long-lived daemon: replacing files on disk doesn't replace the running process.

  1. Keep a way backsudo pacman -Sw jack2 jack2-dbus puts Arch's packages in the cache.
  2. Installsudo pacman -U jack2dbus-nspa-*.pkg.tar.zst; pacman offers to replace jack2 and jack2-dbus.
  3. End the old daemonjack_control exit. stop isn't enough: the old daemon keeps 1.9.22's libjackserver mapped and can't load the new drivers (undefined symbol … IsCaptureChannelNeeded).
  4. StartYour start script or jack_control start; D-Bus launches the new /usr/bin/jackdbus. If PipeWire held the card, a second start clears a "device busy".
  5. Checkreadlink /proc/$(pgrep -x jackdbus)/exe shows no "(deleted)"; GetXruns / GetLoad / GetClientTimings over D-Bus; ~/.log/jack/jackdbus.log.
