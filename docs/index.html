JackBus

JackBus is a successor to JACK2: a realtime audio server and client library for Linux, built on JACK2 1.9.22. It keeps JACK's client API, shared memory and wire protocol exactly as they were, so every JACK application runs on it unchanged, with a stock or a JackBus libjack, 64- or 32-bit. Everything it adds sits beside those interfaces.

  • PipeWire, PulseAudio and ALSA applications. Its shims make each one a JACK client of its own in the cycle, at JackBus's rate and resampled only when it insists: browsers, conferencing clients, players, games and the desktop's own sound, with no sound server in between (§13). The desktop's volume control drives the card's own mixer, and JackBus starts before the desktop (§14).
  • Every sound card, hotplugged. Sound card bridges join cards on their own clocks to one graph, each resampled in the master's cycle with the delay measured on the card (§15). A card plugged in is offered within a second, a bridged card comes back on its own, and the master's card can be unplugged and plugged back while clients run (§14).
  • A harder realtime core. The engine, the ALSA driver and jackdbus reworked, every change measured on the engine itself: no system call on the driver thread but the card's poll and the clients' wakeups, the server's memory locked, late period interrupts covered by a wake timer (§4–8).
  • Failing clients, contained. A client that dies is out of the graph the moment its realtime thread ends; one that hangs or runs late is named and counted, and no longer holds up the rest (§16–18).
  • For tools and new applications. jackdbus calls for session managers and monitors (an application taken out of the graph before it stops, each client's late cycles, bridges added live), and a native client API, nodes over the JackBus socket (§11, §12, §14).

PatchBox, built alongside it, is its patchbay, settings page and session manager (its architecture).

1System overview

Separate client processes, one server process, and the shared memory in /dev/shm between them. Audio never crosses a socket: port buffers live in the graph segment and are read and written in place. Futex words wake each client when its inputs are ready; sockets carry only requests and notifications.

Three planes. The data plane is shared memory: the driver converts the card's mmap area into port buffers in jack-1000-0, clients read their inputs and write their outputs there directly, and an input connected to one output gets that output's buffer pointer (zero-copy). The activation plane is one futex word per client: a client runs when the activation counter for its inputs reaches zero and its futex is signalled. The control plane is two kinds of socket — requests from libjack to the request thread, notifications back to each client's notification thread — plus D-Bus for jack_control and the device reservation PipeWire honours.

What the fork moved. Everything in the amber column is protocol 9 and stays byte-identical, so a stock libjack in any process (a bundled one, Arch's lib32-jack2) still attaches. The changes live in the violet boxes: the RT driver thread no longer issues socket writes or condvar signals (the two bounded queues and the futex event count), the engine's per-cycle loops stop at the highest live refnum, and libjack serializes and snapshots what it used to race on. Since the first edition the server also learns at once when a client's realtime thread ends: the first dashed violet box is the fork's one addition to /dev/shm, optional on both sides, and the rose line is the kernel waking the notifier through it (§16). The second is not in /dev/shm at all: the JackBus socket, through which a client receives those same objects as file descriptors (§11).

2Processes and threads

JACK2 runs its engine and its hardware driver inside one server process — jackd on the command line or jackdbus as a D-Bus service; both link the same libjackserver — and every application is a separate process linked against libjack. Exactly one thread on each side is real-time: the server's driver thread, and each client's process thread.

jackdbus · the server

D-Bus service org.jackaudio.service, started on demand by the session bus; embeds the JACK server. jack_control, qjackctl and Cadence talk to it.

  • Main thread. The D-Bus loop: engine and driver parameters (persisted in ~/.config/jack/conf.xml), start/stop, the patchbay interface. Fork: SIGTERM/INT/HUP are consumed and end the process cleanly (C11); the crash handler only writes and re-raises (C17); control operations are serialized with the request thread (C20); a failed master switch can't wedge it (C19).
  • Request thread. Polls the request socket, the JackBus socket (§11) and every client socket; client open/close, activate, connect, port registration. Takes the engine lock — never the RT thread. Fork: also removes clients whose process died (§16), and queues notifications for a client that falls behind instead of waiting on it (§18).
  • ALSA driver thread, SCHED_FIFO 89. Waits on the PCM, converts samples, runs the engine's per-cycle step and wakes the first clients. Fork: no syscalls besides poll and activation futexes; memory locked (R1); per-cycle loops bounded (§5).
  • Engine notifier and message buffer threads. New in the fork. They drain the RT thread's lock-free queues every 20 ms and 50 ms and do the socket writes and log I/O the RT thread used to do (§6). The notifier's wait is a futex_waitv on its own wake word and the alive slot of every active client, so a client's realtime thread ending wakes it within microseconds (§16).
  • alsa_seqmidi port thread (-X seq). Subscribes and unsubscribes sequencer ports as they appear and hands them to the RT side through bounded rings (C22).

3Shared memory and the wire protocol

The server creates the shared objects; clients map them by name (or, over the JackBus socket, from the file descriptors it hands them, §11). Their layouts, together with the futex-word protocol and the request encoding, are what protocol 9 freezes. The fork never changes a byte of them.

Why the layout is frozen. The server and every libjack compute addresses in these segments independently: a port buffer's zero-copy address, a client's activation counter, the frame timer a client reads in jack_frame_time(). A single moved field reads as garbage in a client built from another tree — which is what upstream's develop did to JackEngineControl (C2), and why the fork is based on the 1.9.22 tag rather than on develop.

Everything that grows or tracks state lives outside. The refnum high-water mark, the RT queues, the notifier and message threads, the dirty-row bookkeeping and the PM QoS file descriptor are all in the server's private heap. The only shared-memory behaviour that changed is who writes when: fewer writes per cycle (bounded resets), smaller copies per graph edit. The one new shared object, the alive-slot file, is separate from all of these and optional on both sides (§16).

4The process cycle

One period of 512 frames at 48 kHz, 10.67 ms, in asynchronous mode (the default). The driver thread wakes on the card's period interrupt, moves samples, runs the engine's per-cycle step and wakes the clients with no upstream dependency; from there the clients wake each other. Not to scale: the driver's share is tens of microseconds.

Async vs sync. In the default asynchronous mode the driver writes the previous cycle's output, wakes the graph and goes straight back to poll(); a late client costs that client's output, not the driver's schedule. With -S (sync) the driver waits for the graph's end node with a timeout and writes the current output — one period less latency, but a stuck client stalls everyone (measured in §24). The engine decides at each cycle start whether the previous graph finished (IsFinishedGraph); if it didn't within the client timeout, it switches state anyway and reports an xrun.

What the fork changed on this path. Read fills a capture port in the cycle its connection takes effect (C24). CycleBegin and RunNextGraph touch only live refnums, and ResumeRefNum skips empty successor slots 16 at a time (§5). The graph-order notification is a TryPush into a bounded queue instead of a socket write() (§6); the "cycle passed" event for waiting control threads is one atomic increment instead of a condvar signal. Sample conversion runs without libm calls (P2/P3). After an xrun the frame timer is re-seeded instead of running backwards (C6), and recovery restarts only the PCM streams (R2).

5Activation graph and per-cycle loops

JACK2 runs clients in parallel wherever the graph allows. Each client has an activation counter in shared memory, reset every cycle to its number of predecessors; every predecessor that finishes decrements it, and the one that takes it to zero signals the client's futex. No central scheduler runs during the cycle.

Start and end node. The freewheel driver (refnum 1) runs as a slave of the ALSA driver in normal operation. At activation every client is connected from it and to it (DirectConnect(1, ref) and DirectConnect(ref, 1)), so each cycle it signals every active client, and every client signals it when done. IsFinishedGraph() is simply "refnum 1's counter reached zero". A client with inputs from the driver and from other clients waits for all of them: its counter counts predecessors, not ports (fConnectionRef holds the port count per client pair; the counter moves only on the first and last port connection between two clients).

Where the per-cycle time went. A perf profile of the server (16 clients, 32-frame periods) put about 40% of its user-space time in three loops over all 256 client slots: ResetGraph (activation counters and timings — shared-memory lines the clients' cores wrote last cycle, so each store is a cross-core transfer), ResumeRefNum (the successor scan, also the top hotspot in every client) and CalcCPULoad. Refnums are allocated lowest-first, so live clients are always at the bottom of the table: the server keeps 1 + highest refnum in use (release store when the table changes, acquire load per cycle) and its loops stop there. The successor scan, which runs in every libjack, reads 32 bytes at a time and only looks at individual entries in a non-zero chunk, in the original order.

6RT side channels without syscalls

Besides waking clients, the driver thread has three things to tell the rest of the server: notifications (graph order, xruns) for the clients, "a cycle has passed" for control threads waiting on a graph change, and log messages. In 1.9.22 each of those is a kernel entry from a SCHED_FIFO thread — and on PREEMPT_RT every kernel wake path takes a sleeping, priority-inheriting lock.

The queue. JackBoundedQueue is a bounded multi-producer/multi-consumer ring with a sequence number per cell (Vyukov's design): a producer claims a slot with one compare-and-swap on the enqueue position and publishes it with a release store of the cell's sequence; head and tail positions sit on separate 64-byte lines. A full queue is not an error path that blocks — the item is dropped and counted, and the count is reported when the server stops (the notifier's 20 ms wait has since become a futex_waitv that also watches the clients' alive slots, §16). Notifications are asynchronous by contract (graph order, xrun callbacks), so up to 20 ms of added delivery delay is invisible; ordering and the threads that run the callbacks are unchanged.

The cycle signal. Control threads (client activate, deactivate, close) wait for "a cycle has passed" so that a graph change is known to be in effect. JackCycleSignal is a futex event count: the RT side increments a generation counter and calls FUTEX_WAKE only if a waiter flag is set — almost never; waiters sleep on the generation with a CLOCK_MONOTONIC timeout. The glibc condvar it replaces took its internal lock on every signal, every cycle, from the RT thread. Logging still formats the message on the thread that logs, but no longer locks or wakes anything; MIDI drops are logged once per burst rather than per event (R8), and the ALSA adapter's RT thread now uses the threaded log function (R6).

7Graph changes: the double-buffered state

The connection state is double-buffered so the RT thread never takes a lock to read it. Writers (the request thread) edit the next state; the RT thread adopts it at a cycle boundary with one atomic operation; readers re-check a counter to detect a switch under them. The cost sits entirely on the writer — which is where 1.9.22 spent 19 MB per edit.

19 MB per edit. With Arch's build options (--clients=256 --ports-per-application=2048) one JackConnectionManager is 19.05 MB. 1.9.22's WriteNextStateStartAux copied all of it into the next state at the start of every write session after a switch: about 38 MB of memory traffic per connect or disconnect, streamed through the last-level cache the RT threads share. While patching at small periods that's gigabytes per second of cache pollution. The fork copies only the used part of each table: the JackFixedArray invariant keeps items compact in [0, count) with EMPTY after them, so the copy stops at the count. A unit test compares the result byte for byte with a full copy (300 rounds, the full 19 MB state).

Waiting for a change. Some API calls (jack_port_connected, the latency queries) sleep up to 1.1 periods if a change is pending, so a caller sees the graph it just requested — except on RT threads, which must never sleep. Threads created with jack_client_create_thread weren't recognised as RT and slept too: 2945 µs measured in a 2667 µs period. The fork marks them like the process thread (R10), and tests for a pending change before reading the thread marker, so the common case reads no thread-local state at all.

8The ALSA driver

jack_alsa.so owns the card. It maps the PCM's ring buffer, waits for each period with poll(), converts between the card's integer format and JACK's 32-bit float port buffers, and drives the engine's cycle. The measurements in this document come from an Intel HDA card, Realtek ALC274 (24 significant bits in S32_LE), at 48 kHz, 512 × 2.

Why the stale buffer. To save work the driver converts only capture channels that have a connection. It asks the graph before the engine's switch (Read() runs first in the cycle), so in the cycle a new connection takes effect the port is skipped — and its buffer still holds whatever was converted the last time it was connected, possibly minutes ago. The client hears a period of old audio. The fork converts every channel while a graph change is pending (IsCaptureChannelNeeded) and zeroes a skipped buffer once when a port stops being connected (SkipCaptureChannel), so the worst case is a period of silence, never old audio. The same logic covers the FireWire driver.

Around the cycle. The poll timeout was computed in microseconds and passed to poll() as milliseconds: 16 s at 512 frames, so a stalled device took that long to be noticed, and stop or buffer-size changes could block as long (C8). An xrun ran the full JackDriver::Stop/Start on the RT thread, restarting slave drivers with thread joins and allocations; the fork drops, prepares and restarts only the PCM streams, with the descriptor array allocated once (R2). A fatal device error now reaches clients as a shutdown notification instead of a silently dead driver thread (C13). After any xrun the frame-timer DLL is re-seeded, so jack_frame_time() doesn't run backwards for a period and take a second to reconverge (C6).

Late period interrupts: the wake timer

On Intel HDA at small buffer sizes it is the period notification, not the audio, that comes late. The driver's interrupt handler drops an interrupt as "too early" when the one before was handled late, or defers it to a worker that loops on msleep(1); meanwhile the DMA position is right all along. A server that waits for the interrupt alone wakes late, and the cycle overruns.

How it decides. Before each wait the driver works out when the period is due, from the position and timestamp the card's last update left in the status page: no system call. It waits for the interrupt until then plus the margin, and after that asks the card for its position itself (hwsync). Adaptive mode only watches at first: a wait that began before its period was due and whose wake, or xrun, came more than half a period later counts as late; three of them turn the timer on, and the log says so once. A cycle that ran long doesn't count (its period was already due when it began to wait). A buffer-size change sends it back to watching. Batch (USB) cards are left alone: their position only moves when they report, so a timer can learn nothing earlier.

9MIDI through -X seq

With -X seq the ALSA driver bridges the ALSA sequencer: every sequencer port becomes a JACK MIDI port (system:midi_capture_N / system:midi_playback_N). A non-RT port thread follows ports as they come and go; the RT thread moves the events each cycle, placing them by the sequencer's timestamps.

The asserts (C22). The hand-over rings between the port thread and the RT side held about 63 ports per direction, and overflow was an assert: 150 sequencer ports at startup, or a burst of new ports while running, aborted the whole server. The fork drops and counts instead — a port that didn't fit is picked up again on the next announcement — and the hash race between the two threads is closed. On hw:PCH, 1.9.22 aborted in update_port_type with 150 ports at startup and in port_event on a 150-port burst (4 of 5 runs); the fork started with 152 MIDI ports and survived every burst.

The idle ioctls (P5). Each cycle, read and write both fetched the sequencer queue's real time with snd_seq_get_queue_status() — an ioctl that takes the queue's lock, an rt_mutex on PREEMPT_RT — whether or not any MIDI was flowing. The time is only needed to place an event, so it is now sampled, together with JACK's frame time, the first time an event needs it in that cycle. 10libjack: the client side

libjack is code running inside every JACK application. Its API and ABI are fixed, but its internals — how it serializes requests, publishes callbacks, keeps per-thread state and shuts its threads down — are free to change, and that is where the client-side races were.

Requests and activation. All of a client's API calls share one request socket. 1.9.22 wrote a request and read its reply without a lock, so two application threads calling at once could read each other's replies and desynchronize the stream for good: 1 599 errors and a hang in the concurrency test, 0 now (C9). jack_activate returned before the process thread had run its buffer-size and thread-init callbacks, so a slow callback made the first cycles late: 13 xruns per activation with a 60 ms callback, 0 now (C10).

Cancellation at close. jack_client_close stops the client's threads with asynchronous cancellation — a cancel can land on any instruction, inside malloc or inside a lock. Switching to deferred cancellation (R9) was rejected: a callback blocked on an application lock would turn into a permanent hang. The fork instead disables cancellation around its own locks (JackNoCancelScope); a cancel that arrives inside is acted on when the scope ends. glibc does that inside pthread_setcancelstate(), i.e. in the scope's destructor, and a C++11 destructor is noexcept: the first version aborted the application. Found by the sanitizer runs; the destructor is now noexcept(false) and a unit test cancels 100 threads inside the scope (aborted on the first before, 100/100 clean after, 64- and 32-bit).

Per-thread state. The RT marker, the notification-thread marker and the per-thread log function were pthread keys. They are now __thread pointers, and x86 builds use -mtls-dialect=gnu2: with TLS descriptors a read is an indirect call to glibc's two-instruction static-TLS resolver, and glibc places a dlopen()ed libjack in surplus static TLS (checked: all three descriptors resolve to _dl_tlsdesc_return). The default dialect would have been slower than the pthread key (3.2–3.5 vs 2.9–3.1 ns) and can allocate through __tls_get_addr after a later dlopen. Initial-exec TLS isn't an option: libjack is dlopen()ed by weakjack users and Wine.

11The JackBus socket

Protocol 9 hands a client names: the shm registry, the segments and a futex file per client in /dev/shm, and a socket of the client's own there that the server connects back to. JackBus adds a second socket beside it, $XDG_RUNTIME_DIR/jackbus/<server>, through which a client receives the same objects as file descriptors. It is the same libjack client on the same shared memory, futex words and alive slot, running the same realtime loop in the same graph; only the way it gets hold of them changes. Protocol 9, the shared layouts and every existing symbol stay as they were.

requests and replies (the JackBus socket) notifications (the socket pair) file descriptors (an SCM_RIGHTS trailer) added by JackBus

The same client, another way in. JackBusLibClient is libjack's own client class with another channel: once the open is through, it maps what it received (SetShmFd, ConnectFd) and runs JackClient's realtime loop unchanged, so every jack_* function works on it and it runs in one graph with protocol-9 clients — of this libjack, of a stock one, in other processes or in the same one, which then shares one mapping of each segment. The server serves the socket from the request thread that serves protocol 9's (one more fd in its poll); it opens the objects it created itself (jack_shm_open_fd only for segments it allocated, a dup of the client's futex fd, the alive table) and passes them. A peer's futex file travels with each kAddClient, opened by name when the notification is sent, just as a protocol-9 libjack opens it when the notification arrives: one sent late to a lagging client (§18), whose client is gone by then, carries no fd, and the client's connect fails as a protocol-9 libjack's would.

Stricter than protocol 9. Only the user's own processes: the directory is the user's, mode 0700, and the peer's uid from SO_PEERCRED must match. A version handshake first; then protocol 9's name check without its open flag, then kBusClientOpen, then protocol 9's requests. The pid the engine records is the socket peer's as the kernel sees it, not the one the client reports (a sandboxed client reports one of its own namespace). A request on behalf of another client's refnum is refused, so is the server's own kNotification, and a client that sends anything out of order is dropped. A request that stops half-way is dropped after 2 s instead of holding the request thread, and with it every other client; on protocol 9's socket it holds the thread until the rest comes. The alive slot is mandatory: the open fails without one, so a JackBus client's realtime thread always holds its slot (§16).

How fds travel. The socket is a SOCK_STREAM unix socket like protocol 9's, because requests are read field by field. A message that carries fds ends with a trailer: one byte, the number of fds, sent with sendmsg() and SCM_RIGHTS (JackFdPassing). Reads of exact field sizes stop before it, and only recvmsg() reads it, with MSG_CMSG_CLOEXEC: a plain read() of that byte would make the kernel close the fds it carries. Every fd a JackBus client holds is close-on-exec, its sockets included, so a program it starts inherits none.

Where it is, and how to use it. jackd and jackdbus alike bind $XDG_RUNTIME_DIR/jackbus/<server> beside protocol 9's request socket, creating the directory if needed; a socket left there by an earlier server of the same user is replaced, anything else at that path is an error, and the socket is removed when the server stops. Without XDG_RUNTIME_DIR, with a directory that isn't the user's or is open to others, or with JACK_NO_BUS_SOCKET=1, there is simply no JackBus socket and protocol 9 is untouched. An application opens a client with jackbus_client_open() (jack/jackbus.h): the arguments of jack_client_open() plus reserved flags, a jack_client_t back. It never starts a server, and fails cleanly (NULL, JackFailure) where there is no JackBus socket: a stock server, or no runtime directory. JACKBUS_TRANSPORT=1 sends every jack_client_open() of the process through it, with no fallback, so that unmodified programs can run over it in tests; jackbus_simple (example-clients/) is jack_simple_client opened this way, with -f to fall back to protocol 9.

12Nodes: the native JackBus API

A node is a client of the JackBus socket with what JACK's API makes applications work around: a process function that gets the whole cycle as a record, port buffers resolved before it runs, notifications as events the application drains from its own threads through a file descriptor, latency as a number it declares, and ports that come and go while it runs without the realtime thread ever waiting. The interface (jackbus_node_*, jackbus_port_* in jack/jackbus.h) is experimental and may still change. Nothing changes for any other client.

requests (the JackBus socket) notifications, then events (eventfd) activation (futex wake) alive slot (robust futex → futex_waitv) JackBus code upstream protocol, unchanged

A node and its client. jackbus_node_open() opens a client over the JackBus socket (§11) and sets every callback on it: libjack's process callback becomes the node's wrapper, and each notification callback (client and port registration, connections, renames, graph order, buffer size, sample rate, xruns, freewheel, latency, properties, shutdown) appends an event. jackbus_node_client() gives the same client to the jack_* API for everything else — connections, metadata, transport — on which no callback may be set. The realtime thread is libjack's own process thread, at the server's priority minus one, in the same loop as any client's: woken by its futex word, signalling its successors, holding its alive slot for as long as it lives. So the server finds a dead node the way it finds any fork libjack client: the kernel marks the slot as the realtime thread ends and wakes the notifier (§16). Under a dying server a node gets a SHUTDOWN event, its process function stops being called, and jackbus_node_close() returns.

The cycle record. The wrapper fills it from the server's frame timer — the double-buffered DLL state in JackEngineControl that jack_get_cycle_times() reads — and two vDSO clock reads for the offset between CLOCK_MONOTONIC_RAW (JACK's clock) and CLOCK_MONOTONIC: no system call. frame is JACK's frame time, carried on in 64 bits: it advances by nframes each cycle, jumps at an xrun, and advances once by the new size at a buffer-size change. The times are nanosecond fields, filled from the server's microsecond timer for now; while freewheeling only frame and cycle mean anything. The flags say what a process function otherwise has to work out itself: the first cycle since activation, the first after an xrun, freewheeling, transport rolling.

Buffers once, and a zero buffer. Before the process function runs, the wrapper resolves each port's buffer once — what jack_port_get_buffer() would return — except that an unconnected audio input gets one zero buffer shared by every node of the process: made at the open, mapped read-only with its pages populated and locked, never cleared again. A node that writes into it crashes with SIGSEGV instead of silently feeding its own garbage back in. jackbus_port_audio() and jackbus_port_midi() only hand out what was resolved; MIDI keeps JACK's own buffers, for the jack_midi_* functions.

Events, not callbacks. JACK runs its notification callbacks on a library thread that must not call the server. A node's notifications arrive in a bounded queue instead, appended on that thread under a mutex, and an eventfd becomes readable; the application drains them with jackbus_node_next_event() from any thread but the process function, and may call anything while it handles them. The buffer-size call libjack makes on the realtime thread as it starts is not a change and is not queued, so nothing is ever written from the realtime thread. A full queue (1 024 events) drops what follows and counts it: the next event read is a LOST with that count, the sign to read the graph again.

Latency as data. A latency callback replaces JACK's default propagation for its client, so the node's callback does what the default does — each side's widest range taken to the other side — and adds the frames the node declared with jackbus_node_set_process_latency(), at any time; a LATENCY event follows.

13The shims: PipeWire, PulseAudio and ALSA applications

Applications written for PipeWire, PulseAudio or ALSA reach JackBus directly, each one a JACK client in JackBus's cycle, at its rate and period, through three shims built on the node API (§12): jackbus-pw takes the place of libpipewire-0.3, jackbus-pa of libpulse, and jackbus-alsa is an ALSA plugin, the jackbus device. No PipeWire or PulseAudio server is in the audio's way. An application's own work (decoding, mixing, effects) stays in its own threads, as with any sound server; in JackBus's cycle a shim only moves one cycle of frames between the application's buffer and its ports, converting the sample format, and resampling when the application insists on another rate. That realtime side makes no system call but JACK's own futex.

An application is a JACK client. Each application gets one node (§12): a JACK client named after it, with a port per channel of each stream, in the graph like any other client, routed and session-saved by PatchBox, removed by JackBus's own death detection if the application dies. A node is in the cycle only while a stream is connected. Where an application processes in the audio cycle (a pw_filter, ossia's engine), its process runs in JackBus's cycle, sample-accurate; where it writes ahead into a buffer (a pw_stream without RT_PROCESS, every PulseAudio and ALSA stream), the node moves one cycle of that buffer.

In the cycle, and beside it

A stream that writes ahead has a ring between the application and its ports: PulseAudio's of 131072 frames, an asynchronous pw_stream's of 32768, and for ALSA the application's own buffer, which alsa-lib maps (mmap_rw). The node's realtime thread copies one cycle each cycle, converting at the boundary (float, S16, S24 in 32, S32) and applying the stream's volume, cork, prebuffering, flush and drain. A cycle the ring can't serve whole is an underflow (PulseAudio), an xrun reported as EPIPE (ALSA), never a wait. The application's side is woken by a timer phase-locked to the cycle, armed from the node's published cycle record (next_ns, period_ns): a timerfd in ALSA's poll set, a time event on PulseAudio's main loop, half a period for an asynchronous pw_stream. Positions and timing are JackBus's frames, published by the realtime thread in a sequence-locked snapshot and interpolated within the cycle, so snd_pcm_delay(), pa_stream_get_time() and pw_stream_get_time_n() are exact: the ring's fill plus the ports' JACK latency.

Two sides, one clock. The realtime side never blocks and the application's side never runs in the cycle: it is woken when the ring will have room (or, recording, data), computed from the cycle clock the node publishes, so it wakes once per need, phase-locked to the cycle, not on a free-running timer. A resampler, when one is needed, runs at a fixed ratio: the application runs on JackBus's clock, so nothing drifts.

Async: outside the cycle

The copy above runs on a realtime thread inside the application's process, so a frozen or starved application (Teams paging, a browser stalled) makes the whole cycle late and every client is told of xruns. With async = yes for a family (pa., pw., alsa.), each stream is an async endpoint instead: its ring lives in a sealed memfd shared with JackBus (common/JackBusEndpoint.cpp), and the master driver copies it to (from) the ports itself, after the engine's Process and before any client is woken. Connections to an endpoint's ports make no activation edge, and a node with only endpoints has no realtime thread. The application's own audio threads (rtkit ones too) are untouched. The cost: what another client sends to an endpoint arrives one cycle later. PipeWire filters, RT_PROCESS and MIDI streams, and resampled ALSA streams stay in the cycle.

Who copies. Measured (nspa/tests/async-stall.sh): paplay, aplay and pw-play frozen for 2 s beside another client. In the cycle it is told of about 230 xruns; async, of none, it runs every cycle, and the application plays on to its end.

The direct route first, then resampling

Every shim offers JackBus's own rate first, so an application that can use it takes the direct route: no conversion of rate, no added delay. jackbus-pw negotiates in two passes, any format the stream offers at JackBus's rate before anything else, and provides the RateMatch io area and the Latency parameter applications wait for; jackbus-pa presents JackBus's rate as the server's and every device's, so applications that open at the server's rate (the browsers) take the direct route; jackbus-alsa offers it as the rate. Only an application that insists on another rate (a 44.1 kHz file played as it is, a game with a fixed rate) is resampled, by JackBus's bridge resampler (§15) in the node's realtime thread, realtime-safe, at a fixed ratio: a fallback, on by default, chosen per shim (resample), at the quality chosen (resample-quality: 32, 56 or 96 taps). With resampling off, jackbus-pw and jackbus-pa refuse such a stream with the reason, and jackbus-alsa offers JackBus's rate only, as a card at a fixed rate does.

jackbus-pa: libpulse, and who gets it

The client API is JackBus's own: pa_mainloop and pa_threaded_mainloop, the context's states through to READY on the application's main loop, operations delivered by deferred events, buffer attributes as libpulse defines them (the device's latency subtracted under ADJUST_LATENCY; an optional cap per stream, max-latency), timing info and interpolation, sink-input and source-output volume and mute applied to the samples. The rest of libpulse's API (sample specs, channel maps, volumes, property lists, formats) is PulseAudio's own libpulsecommon, which the library links. The devices are JackBus's cards: a sink per JACK client with physical playback ports, a source per client with capture ports, the settings' output and input the defaults; a device's volume and mute are its card's own mixer (below). What a PulseAudio server has and JackBus doesn't answers as a server without it would: no cards or modules, an empty sample cache (playing a cached sample fails, so libcanberra plays the sound as a stream), stream-restore present and empty, device-manager absent. There is no central server: each process knows its own streams, so a volume control lists its own; the devices, though, are the cards themselves, and every process sees the same device volume. Events reach the application as a server's would, from its main loop, never inside the call that caused them (below).

Every program, decided once. The package puts /usr/lib/jackbus-pa in the dynamic linker's configuration, so the dispatcher reaches programs whose launchers replace the library path (a browser's helper, a conferencing client's media process) as well as the rest. Each of the 378 functions is a jump through a table that the constructor fills from one implementation for the life of the process. With the setting off it is PulseAudio's own library, and nothing changes; with it on, JackBus's while JackBus runs, PulseAudio's (PipeWire) while it doesn't. The functions are looked up in the chosen libraries' own ELF symbol tables (GNU hash, default versions), never through dlsym: a program that interposes dlsym to hand back wrappers of its own, which then call "the real function" through libpulse, would otherwise send the dispatcher's table back into its wrappers, a loop. A program started before JackBus stays on PipeWire until it is restarted.

The desktop: its volume control, its sounds

A desktop's sound is libpulse in several of its processes. In Plasma: the volume applet and its on-screen display in plasmashell, the volume keys in kded6, the Sound and System Sounds pages in System Settings, and the event sounds (a notification, a volume change's click), which libcanberra plays from whichever application raises them. GNOME's are the same libraries. Started after JackBus, which jackbus.service sees to (§14), each of them gets jackbus-pa through the dispatcher: the applet lists JackBus's cards as its devices, its slider and the keys set the card's own volume, and an event sound is a short stream, a node of its own while it plays.

One volume, held by the card. Without a central server each process has its own jackbus-pa, so the device volume can't live in any of them: it is the card's hardware mixer, which every process opens for itself and the card keeps. The applet, the keys, System Settings and alsamixer then show and set one value, and a change from any of them reaches the others through the mixer's own events. Events from the main loop, as a server's

A PulseAudio server answers later: a stream's end, a device's change, a stream added or removed reach the application through its main loop, after the call that caused them returned. Applications are written for that, and jackbus-pa keeps it, although it has nothing to wait for: subscription events are queued and delivered from a deferred event on the application's main loop, as are a disconnected stream's TERMINATED and a moved stream's callback.

A server's order, kept. libcanberra's PulseAudio driver ends a sound from the stream's drain callback, holding the lock that guards its outstanding sounds, and its subscription callback takes the same lock to find the sound a removed stream belonged to. With the event delivered inside pa_stream_disconnect(), the main-loop thread blocked on its own lock: after the first event sound no other played, and destroying the context (a settings page closing) waited for that thread forever. Delivered from the loop, as PulseAudio's server does, the lock is free by then. The test (canberra.sh) plays three sounds without a callback, three with one and one cancelled while it plays (the first recorded from its port: a continuous 440 Hz sine), and each context must close within a time limit: the earlier library hung on the first.

An external ALSA plugin (ioplug) whose ring is the application's own buffer: pointer returns the position in JackBus's frames, delay the buffer's fill plus the ports' latency (and what a resampler holds), an xrun is EPIPE as on a card, and the poll descriptors are the node's timer and event fd. 50-jackbus.conf defines pcm.jackbus with the options NAME, SERVER, AUTOCONNECT and FALLBACK. With a fallback, the device opens that PCM instead while JackBus isn't running (its socket checked first, so libjack prints nothing), or when its socket is there and the server isn't; a fallback that leads back to the device fails instead of looping. Limits

  • PulseAudio's monitor sources (a recording of what a sink plays: OBS's "Desktop Audio") aren't there; a JACK input does that in JackBus.
  • No central PulseAudio server: a volume control sees its own process's streams, not other applications' (their levels are set in the graph). Device volumes are the cards' own mixers; a device without one (a card with no volume control, a client's ports) keeps 100 %.
  • The choice is made as a program starts: one started before JackBus keeps PipeWire until it restarts. For the desktop's own processes, jackbus.service starts JackBus first (§14).
  • Flatpak and other sandboxed runtimes bring their own libraries: they stay on PipeWire. Bluetooth audio is PipeWire's.

The hand-over. Card ownership is negotiated on the session bus (org.freedesktop.ReserveDevice1.Audio0): JACK requests the name with the highest priority and PipeWire gives it up. The reverse is automatic — when JACK lets go, WirePlumber acquires the card for its own ALSA node and re-applies its stored route volumes. Two practical consequences surfaced during this work: a JACK start right after PipeWire took the card can find the PCM still open for a moment ("device busy", a retry starts it; stock 1.9.22 behaves the same), and anything muted on the card while JACK was stopped gets un-muted by WirePlumber, which the hardware test harness now guards against (§22).

Engine parameters through D-Bus. Everything settable on jackd's command line is an engine or driver parameter of the control API, so the fork's PM QoS option is available to jackdbus as well: jack_control eps cpu-dma-latency 0 holds a 0 µs request on /dev/cpu_dma_latency while the server runs and releases it when it stops (default off; worth it at 64–128 frames, not at 512).

At login, before the desktop

A program decides as it starts whether its libpulse is JackBus's or PulseAudio's (§13), and the desktop's own sound (the volume applet, the keys, the event sounds) starts with the session. So JackBus has to be running before the desktop's processes start, or they stay on PipeWire for the session. An autostart entry running jack_control start comes too late: XDG autostart runs after the desktop's own units, and on one login Plasma's shell started at 10:07:00 and the entry's start at 10:07:03. The package's user unit, jackbus.service, starts JackBus earlier, through jackdbus.

First the server, then the desktop. The unit is a call, not a server of its own: it asks the session bus for org.jackaudio.service, which activates jackdbus, and tells it to start, with the settings PatchBox and jack_control saved. The desktop's units are ordered after it, so by the time plasmashell and kded6 load libpulse, JackBus's socket is there and the dispatcher gives them jackbus-pa. Stopping and starting the server later works as before; programs started while it is stopped get PipeWire, and keep it until they restart.

The master's own card unplugged

In 1.9.22 an unplugged card makes the ALSA driver fail, the server stops processing, and every client is told it shut down: Ardour and the rest drop. Under jackdbus, JackBus keeps the graph running on the dummy driver and goes back to the card when it returns.

Measured (unplug-survive.sh, an isolated jackdbus on a ZOOM U-44 at 256 frames, a client writing zeros to system:playback_1 and reading system:capture_1, unplugged by hand): the dummy took over and the client ran on at 188 cycles a second with both connections, with no shutdown; once replugged, the server was back on the U-44 with the connections restored and the client still running; jackdbus's file descriptors 27 before and 27 after. jackd without jackdbus, and other driver failures, behave as in 1.9.22.

Device reservations, and the bridges

A JACK server holds each card it uses through the session bus's device reservation (org.freedesktop.ReserveDevice1.Audio<n>), so the desktop's sound server lets go of the card and leaves it alone. In 1.9.22 the table had room for two names (the master's capture and playback cards), wrote slot count even when it was taken, never freed one, and counted down for names it didn't hold. Both jackd's and jackdbus's tables now hold twenty, reuse free slots, are locked (the bridge monitor reserves from its own thread), and count a name asked for twice: a bridge on another device of the master's card shares the master's reservation, and removing it no longer releases the master's. Each sound card bridge (§15) reserves its card the same way, keeps the reservation while the card is unplugged, and moves it if the card comes back under another index; jackdbus lists, adds and removes bridges (bridges, AddBridge, RemoveBridge, GetBridges), and its /dev/snd watch bridges a listed card the moment it is plugged in.

The card's mixer, the user's own

While JackBus has let go of a card (a restart, an update), the desktop's sound server may take it and apply its own card profile: outputs switched, levels moved. jackbus-mixer save <card> (PatchBox's Mixer tab: Save as my settings) keeps the card's simple-mixer controls, raw values per channel, in ~/.config/jackbus/mixer/<card id>.state, and JackBus puts them back whenever it opens the card: the ALSA driver's open and a bridge's, the card plugged back in too. Nothing saved, nothing restored (linux/alsa/jackbus_mixer_state.c; nspa/tests/mixer-state.sh on the test control plugin, the driver's open with a null PCM).

15Sound card bridges

A second sound card runs on its own crystal, and two crystals never agree: a few parts per million apart, the cards drift by a frame every few seconds. JACK2 offered a slave driver, which needs the second card clocked by the master's (word clock, S/PDIF), or a separate resampling client (audioadapter, zita-a2j) with a fixed margin. A bridge joins the card the way the master's own card is joined: its ports are physical ports, filled and emptied by the master in its own cycle, while a thread of the card's own moves the card's frames through a lock-free FIFO and a resampler keeps the two clocks apart. Bridges come and go while the server runs (jackd --bridge, jackdbus's bridges setting, PatchBox's Devices tab), and the delay each card needs is measured, not guessed.

Two threads, no waiting. The master runs every bridge from its own thread, at two points of its cycle. Right after its own Write, each bridge takes what it will play — the previous cycle's port buffers, as system:playback in asynchronous mode — into memory of its own: a copy, nothing resampled yet. Once the first clients have been woken, each bridge fills its capture ports and signals the clients that read them, then resamples what it took for its card: the resampling runs while the clients run (the next figure). Neither side ever waits on the card: if the card side is late, the graph side fades out and places its delay again; if the graph side is late, the card side plays silence for positions nothing was placed for. The card has a thread of its own, at the server's priority minus one, that wakes on the card's interrupts (with a timer behind them, §8) and moves frames between ALSA and the FIFOs.

One time base. The cards stamp their positions on CLOCK_MONOTONIC_RAW; the master's cycle start comes from its frame timer, and is put on the same clock by an offset measured each cycle. Each direction keeps a clock model of its card: a second-order DLL over (position, time), whose bandwidth narrows as 0.5/t from 1 Hz to a 0.01 Hz floor, with an outlier gate and a relock when its mean error drifts past three standard deviations. The graph side reads the model at the cycle start, so it knows where the card is now, between the card's own updates.

One integrator. The resampling ratio is the ratio of the two measured clocks (feed-forward) times a small correction from the delay error, proportional only: the clock model is the only thing that integrates, so the loop has nothing to wind up. It acquires wide (1 Hz for 4 s), then locks narrow (0.05 Hz). A delay error beyond half a master cycle is not drift but a break (a master xrun, a card restart): the delay is placed again at once, by moving the read point, with a 5 ms fade.

Off the wake path. The first clients of a cycle are woken at the slaves' resume, the freewheel driver's, which every client waits for. The bridges used to resample before it: a bridge's playback right after the master's Write, its capture after the master's own resume. Every client in the graph, bridged or not, started the whole resampling time late. Now the bridge only copies before the graph runs (the mix of what is connected to each playback port; one connection is the other client's own buffer, which that client writes again once woken; nothing connected is silence, as the cleared port buffer was), and after the slaves' resume it fills its capture ports, signals their readers, then resamples what it took. With -S this comes before the slaves' write, where the master waits for the graph's end, which needs the bridges' readers signalled; a sync cycle that does not run the graph (the last one unfinished) still plays what it took. The same input reaches the same playback code, capture's timing is the cycle's start as before, and nothing changes for clients, shared memory or the protocol. The cycle trace marks the playback where it now runs (§20).

Why the card side measures. Capture fails when, at the master's cycle, the frames it needs are not in the FIFO yet. How late the newest frames are is a sawtooth: it grows until the card delivers its next transfer, then drops. The master meets it at one phase per cycle, and that phase drifts with the clocks' difference: at a few ppm, a full sweep takes minutes, and a cycle period that is a multiple of the card's sits on one phase for good. The card side meets every peak: just before it writes a delivery into the FIFO, it reads the card's clock and notes how late the FIFO is. A few seconds of that is the true worst case, whatever the phase.

Measured, then followed. The delay is first placed safe: capture learns the card's lateness for a second (the master's samples and the card side's peaks), playback the card's lead; a 2 ms margin goes on top. After 20 s locked, the target moves to the worst the card side met plus 0.75 ms, at 20 ppm: a frame a second at 48 kHz, a pitch change of 0.03 cents, inaudible; the loop follows a few frames behind, on the safe side. A worse case later eats into the 0.75 ms: by a quarter of it or less, the target slides up the same way; by more, it is placed again at once. The ports report where the delay is going, once, not every frame of the slide. Playback is the mirror image: the card side notes, at each fill, how far ahead of the card's position it needed frames.

Learned once. What a card needs (how late its capture comes, how far ahead its playback takes frames) is the card's, not the moment's: a card xrun, a replug or a new master buffer size places the delay again at once, with what was learned and measured. Only a new bridge, or a new sample rate (which sets the bridge up afresh), learns again.

Found by counting. Both came to light only when the bridge started reporting what it had been quietly absorbing: playback positions it filled with silence, capture underruns, the card's own xruns. They now reach jackdbus's log (the first at once, then at most once a minute) and the bridge's status. The tests that judged playback quality had run on snd-aloop, which takes frames when they are due, as an interrupt-driven card does.

How the others size it. zita-a2j's target is its card period plus JACK's plus the filter: the floor, with nothing set aside for jitter. PipeWire's follower uses its quantum plus a headroom that is fixed: a configured value, a whole period more for batch (USB) cards in timer mode, at least 32 samples for capture; it adapts its DLL's bandwidth from the error's statistics, not the headroom. CoreAudio's aggregate devices trust each driver's declared safety offset. None measures the card at run time; ALSA drivers declare no safety offset, so here the bridge measures it.

16When a client dies

A client process can end at any moment — killed, crashed, closed by a session manager. Until the server takes it out of the graph, every cycle waits for it. 1.9.22 learned of a death only from the client's sockets closing, and the kernel closes a dying process's files after it has torn down its memory: for a large process, hundreds of milliseconds of stalled cycles. The fork learns it from a step the kernel takes first.

The kernel's order. do_exit() handles a thread's robust futexes at the very start of exit_mm(): futex_exit_release() walks the thread's robust list, and handle_futex_death() sets FUTEX_OWNER_DIED in each lock the thread held and wakes one waiter. Only then is the address space torn down, then the files closed (exit_files()), then the parent notified (exit_notify(), where a pidfd becomes readable). The robust-futex step happens whichever way the thread ends, and it is microseconds after the signal. (Checked in the Linux-NSPA 7.3.3 source.)

One step out. Taking a client out of the graph used to publish each disconnection separately, notify every client of each, and remove the client's activation edges last — every cycle until then waited for it. Now all of it goes into one write session of the double-buffered state (§7): the realtime thread switches to the whole change at once, and the switch is forced at the next cycle. The notifications follow, and none goes to the dead client itself: no broken-pipe errors, and its ports are announced gone once (1.9.22 announced them twice).

The alive slot. The server creates /dev/shm/jack_alive.<uid>_<server>, one 64-byte slot per client refnum. A fork libjack makes its client's slot a process-shared robust mutex — in its own glibc's layout, 64- or 32-bit, both of which begin with the futex word — and its realtime thread locks it when it starts and never unlocks it. The server only ever reads and CASes that first word (owner TID, FUTEX_WAITERS, FUTEX_OWNER_DIED): it sets FUTEX_WAITERS so that the kernel wakes it, and the notifier sleeps in futex_waitv on its own wake word and every watched slot at once. The file is the fork's one addition to /dev/shm, and optional on both sides: a stock libjack never opens it (its clients fall back to the next page), and a fork libjack facing a server without it does without. A client of the JackBus socket receives the table as an fd and must hold its slot: its open fails otherwise (§11), so a node is always found this way (§12).

/proc, for any libjack. When the graph does not finish, the realtime thread does one relaxed store and, at most every 100 ms, wakes the notifier, which asks the request thread to look. The request thread checks each unfinished client's process through /proc: the pid comes from SO_PEERCRED on the client's socket (the pid as the server sees it, across PID namespaces), the start time tells it from a later process with the same pid, and the entry's owner must be the client's uid. Exiting or gone: the client is taken out of the graph at once, and removed after the switch. A client found alive is left alone for 100 ms; the server never decides from timing that a living client should go.

The socket. 1.9.22's only signal remains the last resort. It arrives after the memory teardown, and not at all while another process holds the sockets: libjack doesn't set close-on-exec, so a child the client forked inherits them, and in the killfork test the graph stalled 4.7 s until the child went too. The slot, or /proc (which looks at the client's own process), finds the death first.

A session manager knows beforehand. No signal is earlier than being told: a session manager that started an application can ask jackdbus to take its clients out of the graph before it stops it. That works with any libjack inside the application, and even when the application is killed in the middle of its callback — the one case the slot can't help a stock libjack with. The calls are described with the rest of the D-Bus interface in §14.

17Late clients: catch up, report, count

A client that overruns its period is alive and busy: nothing to remove. The fork keeps how JACK lets a late client catch up, reports each failing cycle once and names the client behind it, and counts per client how often, and by how much, it ran late — without slowing a cycle in which nobody did.

Catch-up, kept. At the next cycle start the engine resets the graph and the late client's inputs trigger it again; when it finishes the late cycle it finds its futex already signalled and runs the next one straight away. After a one-off spike it has processed every block of its input; what was late is its output for one cycle. Making it skip its next trigger instead, as CoreAudio does with an overloaded client, would relieve it, but in a graph its late finish has already signalled its successors, and the skipped block of input is lost to it for good: a recorder gets a gap, an effect's state jumps, and a note-off in that block is a stuck note. That was designed, analysed, and dropped before a line of it shipped.

One xrun per failing cycle. 1.9.22 sent an xrun notification for every client it found unfinished, so a client that died or hung in the middle of a chain counted as several xruns, each with its own log line, and jack_get_xrun_delayed_usecs() kept returning whatever the driver measured last (698 s was seen). Now a failing cycle is one notification and one line naming up to four unfinished clients, with their state and how long since each was triggered, and the delay value is this xrun's: the longest time an unfinished client had been in its cycle.

Late cycles, for free. A late client means an unfinished graph: on a cycle that finished, nothing is counted and nothing is read. On a cycle that didn't — already the engine's slow path, where it reports the xrun — each client in the graph that was triggered and hadn't finished is counted. A client still waiting for one of its inputs isn't: the one it waits for is, so the count points at the slow client, not at what follows it.

Cycle lengths, on demand. How close each client runs to its deadline, even when nothing is late, needs every client's wake and finish times every cycle. That costs the realtime thread about 50 instructions per client, so it runs only within a minute of the last GetClientTimings call: a monitor that shows the numbers polls, and pays while it watches. A late cycle overwrites nothing until its catch-up does, so it is measured up to the client's next wake (exact in the usual back-to-back case), and while it lasts, up to now. In freewheel mode nothing is counted.

18Slow notification clients

Notifications reach each client's notification thread over its own socket, and some of them wait for a reply. In 1.9.22 the request thread waited for each of those under the engine lock: one client that answered slowly — a plug-in host busy in a callback, a debugger stop — held up every other client's open, connect and disconnect, and one that stopped reading blocked the server for good.

Lagging. A client lags when it doesn't answer a latency notification within 500 ms (each client gets two after every graph change, in graph order), or when its socket couldn't take one more notification without blocking. While it lags, its notifications are queued in order and sent as it catches up, from the request thread every 50 ms; the replies it still owes are counted and read as they come, so a late reply is never taken for a later one's. It receives every notification, in order, some of them late; only a client that doesn't read long enough to fill its queue (4 096) loses some, counted and reported, followed by a graph-order notification so it re-reads the graph.

Which waits remain. Buffer size, sample rate, freewheel, a new client's registration, activation and session notifications are still waited for as in 1.9.22, up to 2 s: the client has to have handled the change before the server goes on. A lagging client first gets the chance to catch up within that same time. Known edge, of the same kind as 1.9.22's after its timeout: a lagging client learns of new clients late, and a client connected after it can miss cycles until then.

One write per notification. A notification was eight write() calls, one per field; it is one now, with the same bytes on the wire. That also makes the "room in the socket" check exact: a notification is either written whole or queued whole.

19Failure modes fixed

Five failures that cross process boundaries, each reproduced before it was fixed. Step through them with the arrows.

C1 · found the hard way. During the audit a test server sharing the live jackdbus server's /dev/shm unlinked that server's graph segment. All of a user's servers share one registry, and jack_destroy_shm() unlinked by registry index without checking who allocated the entry. The wrong index came from an object-lifetime bug that only LTO exposes: the segment info was written before placement-new started the object's lifetime, and GCC's lifetime dead-store elimination dropped the writes — the same root cause as upstream's long-open LTO crash (#485). Since then every test server runs in a private user/mount/IPC namespace with its own tmpfs on /dev/shm.

C25 · found on hardware. A client process that survives its server — hung, or ignoring the shutdown callback — keeps its futex file mapped. 1.9.22 left those files in /dev/shm when it stopped with clients connected, and the next server's Allocate() reopened an existing file instead of creating a fresh one. A new client with the same name then shares its futex word with the old process, which consumes every other wakeup. The first hardware run found it: an orphaned test client cost a 1.9.22 server 906 xruns in 20 s.

C6 · every xrun. After an xrun the driver resets the frame timer. 1.9.22 set the current wakeup but not the next, so for about a period Time2Frames ran backwards (or divided by zero) and the DLL needed about a second to settle. Clients that schedule by frame time — MIDI output, transport, anything using jack_frame_time() — saw time jump. The fork re-seeds the DLL and publishes a consistent state; libjack also guards against a non-positive period.

db5.3 · a packaging bug with runtime effects. The metadata store is a Berkeley DB environment in /dev/shm shared by the server and every client. A process linked against another Berkeley DB version can't open an environment created by the first one, and silently loses metadata. The fork's first build picked up the system's db 6.2; Arch links db5.3. The same messages appeared earlier in this work whenever a 1.9.22 client met a fork server — the test that now gates it fails 4/4 against a 6.2 build.

C27 · seen as clients left behind by test runs. The notification thread handles kAddClient and kRemoveClient with libjack's process-wide synchro mutex held, and opening the new peer's futex file is a cancellation point. jack_client_close() cancels that thread and then takes the same mutex: cancelled while it held it, the thread left it locked, and the close waited forever. It takes a client being added while another closes, which a server starting with sound card bridges while applications come and go makes likely; bridge/start-race.sh reproduces it, and also watches the server's side (a refused client, a bridge's futex gone), a separate fault seen twice with two USB bridges and 18 clients opening at start, and not again in 50 starts since (§24). C27 and C28 are the identifiers used here; C28 changed no behaviour when it was fixed, but the JackBus socket's read timeouts depend on it.

20Performance, measured in the engine

Every performance change was measured on the running engine — real clients, the same server, interleaved A/B runs, perf counters per cycle — and kept only if no configuration got slower. Hot-loop microbenchmarks were used to explore, never to decide: one change that won 2–3× in a hot loop lost 30–40% in the engine and was reverted.

Method. Server and client CPU per cycle come from perf stat on the processes (user space, instructions and cycles) divided by the cycles in the window; the critical path is what the last client of a chain records as finish time − cycle start, i.e. what DSP load measures. Variants run interleaved in balanced order (ABBA) against the same server build, in an isolated namespace, on one CPU model; where the result was noise-bound (C-state wake-ups at 2 clients), the run was repeated with a 0 µs PM QoS hold to separate code from power management.

The cycle trace and the harness

Perf counters say how much a cycle costs, not where in it the time goes. JACK_CYCLE_TRACE=<file>, set when the server starts, has the master note in nanoseconds on CLOCK_MONOTONIC_RAW (the clock JACK's microseconds come from) when each part of its cycle ends: its wake-up (ALSA: the poll's return), Read, Write, the bridges taking their playback, Engine::Process, its own resume, the slaves' resume (the freewheel driver's, where the first clients wake), the bridges' capture and their playback, now after the wakes (§15), and the slaves' write (with -S, the wait for the graph's end). At the next cycle it also copies the clients' own timing records of the cycle that ended — signalled, woken, finished: the microseconds every libjack writes — for the refnums below JACK_CYCLE_TRACE_CLIENTS (48). The cycles go into a ring allocated and touched at start (JACK_CYCLE_TRACE_CYCLES, 16 384), the oldest overwritten; when the server stops, after the master's thread, the ring is written out as text with the graph as it was (each refnum's name and the refnums it signals), and a server started again writes <file>.1 and so on. Off, the default, each mark is a load and a branch; on, a vDSO clock_gettime. Nothing changes for clients.

21Compatibility envelope

"Drop-in" is tested, not assumed: every combination of server and libjack that can meet on a desktop runs the same stress client, and the cross-process state that isn't covered by protocol 9 (the metadata database) has its own cross-build test.

What makes this hold. The fork changed no shared layout, no futex semantics and no request encoding; the develop request rework it took writes the same fields in the same order (all 96 field reads compared), only as one complete packet. Everything new — the refnum bound, the queues, the dirty-row bookkeeping — lives in the server's private memory, and the client-side changes (request lock, snapshots, TLS, the chunked scan) only change how libjack's own threads coordinate. What libjack gained is additions: fifteen jackbus_* functions (jack/jackbus.h), which no existing application calls, beside every symbol it had. The package provides jack2=1.9.22, so packages that depend on it, Arch's lib32-jack2 included, stay installable.

The alive slot, cell by cell. Fork libjack on this server, 64- or 32-bit: a dying client is found through its slot (the 32-bit glibc's mutex starts with the same futex word). A stock libjack on this server never locks a slot and is found through /proc when the graph waits: one xrun per kill instead of hundreds, none if a session manager detaches it first. A fork libjack on a stock server finds no file and does without. Kernels without futex_waitv (before 5.16): the slots are polled every 20 ms.

The JackBus socket, cell by cell. It is a second door to the same server, not a change to the first: protocol 9's socket, segments, futex words and request encoding are what they were, and its clients — a stock libjack, a fork libjack opened with jack_client_open() (unless JACKBUS_TRANSPORT=1 asks for it, §11) — never touch it. A JackBus client (jackbus_client_open(), a node) runs in the same graph as they do, sample-exact in chains with this libjack's protocol-9 clients and the system's 1.9.22 libjack, in either order, and in the same process as a protocol-9 client. Against a stock server, or without a runtime directory, there is no JackBus socket: the open returns NULL with JackFailure and starts nothing, and an application that wants to run anywhere falls back to jack_client_open(), as jackbus_simple -f does. A 32-bit application loads Arch's lib32-jack2, a stock libjack (the package ships no 32-bit one): for it the socket does not exist.

22Validation harness

Tests never touch the live audio session. All of a user's JACK servers share one shm registry and its SysV lock, whatever their names — which is how an early test unlinked the live server's segment (C1) — so every test server runs in private namespaces, with a private runtime directory for its JackBus socket; the hardware tests stop the session explicitly and restore it.

Why a watchdog. The first hardware run muted the card once at the start; one second after jack_control stop WirePlumber took the card and re-applied its own volumes, and the speakers were live for about 90 s of 64-frame tests until noticed. The harness now keeps a watchdog in its own session for the whole time JACK doesn't hold the card, checks the mute before and after every test server starts (with retries, aborting if it can't), restores in a safe order, and warns if WirePlumber persisted a muted route. NSPA_HW_MUTE_SELFTEST=1 exercises the watchdog alone with an inaudible S/PDIF switch.

Sanitizers, and what they can't run. Under TSan, libjack's asynchronous cancellation of a client's threads (at deactivate and close) aborts the instrumented client — a TSan limitation, documented in the suite — so TSan runs are gated on reports, not on client results; the jackdbus tests also run against a TSan server with uninstrumented clients, where all pass. The races it reported, one of them older than the fork, are fixed with atomic accesses that leave the shared memory layout and the client API as they were. TSan doesn't see the graph's futex ordering, so libjack annotates it in TSan builds only: a release when a client signals, an acquire when its wait returns, and since two clients chained in one process showed a false report, a release before every activation-counter decrement too, also by a client that leaves the signalling to another (elsewhere the annotation is empty, and the objects are byte-identical). bus.sh, the JackBus socket and nodes: 24 checks under ASan, 0 failures and 0 reports; 0 reports under TSan. The bridges' change of order (§15): the suite under ASan + UBSan, 65 passed and 0 reports, 0 TSan reports, and snd-aloop servers on the regular, ASan and TSan builds without a report.

A private runtime directory. Since the JackBus socket lives in $XDG_RUNTIME_DIR, nspa/run-isolated.sh mounts a tmpfs over it inside the namespace (or makes one under the private /dev/shm when there is none): a test server's socket can never land in the user's real runtime directory, and a test can't reach the session's PipeWire or D-Bus sockets there.

What was measured and deliberately left alone, what remains untested on hardware, and where larger gains would have to come from.

Not covered yet

Implemented without the hardware to prove it, or still to be looked into.

  • jackd without jackdbus: an unplugged master card still ends the server, as in 1.9.22; under jackdbus the dummy stands in (§14).
  • -X raw: non-blocking wake pipes are in (R3); drain and thread priority unchanged; one failing raw MIDI port still stops the I/O thread for all (C21, not done).
  • "Device busy" right after a PipeWire takeover: a bridge retries its card once a second; the master's own open still has no retry.
  • FireWire (FFADO): built like Arch's package, not tested (no FireWire hardware to test with).
  • Sound card bridges: not yet measured against PipeWire's follower on the same cards (only its formula is compared, §15); a card whose rates exclude the master's runs at its own, resampled (untested on hardware); PatchBox offering a newly plugged card a role.
  • A refused open at start. Twice, with two USB cards bridged and 18 clients opening as the server started, a bridge's futex was destroyed under it and every later client open was refused. Not seen again in 50 such starts; bridge/start-race.sh watches for it (§22).
  • The JackBus socket in a sandbox. Tested with an empty, private /dev/shm, not yet inside a Flatpak. There the client's metadata store (a Berkeley DB environment in /dev/shm) is its own, not the one the server and other clients share: metadata does not cross the JackBus socket yet.
  • Nodes. The API is experimental and may still change; the cycle record's nanosecond times are filled from the server's microsecond frame timer.
  • The shims (§13). No PulseAudio monitor sources yet (a recording of what a device plays, as OBS's desktop audio uses); a volume control sees only its own process's streams; a program started before JackBus stays on PipeWire until it restarts (the desktop's own processes don't: jackbus.service, §14); a card without a hardware volume control keeps a fixed device volume. Not yet tested through jackbus-pa: Wine's winepulse.
  • Xruns when apps start or add tracks. In real use they come from the app's own callback (Ardour busy for just over one period during a load), not from the server; in async mode the other clients' audio is untouched. Next: measure with GetClientTimings during app start, track adds and plug-in inserts.

Larger directions

Where further gains would come from, and what they cost.

  • The JackBus API beyond nodes (§12), beside libjack's, which stays as it is: control, bridges and session hooks for the applications that want them.
  • Segments of the JackBus socket's own. The socket already hands a client the server's objects as fds (§11); what it makes possible next is memfd segments, sealed, optionally on huge pages, sized to actual use instead of a fixed 107 MB, for what only JackBus clients map. Protocol-9 clients keep today's named segments, so the full benefit comes only where every client opens over the socket.
  • The scheduler. What remains per cycle is wake-up latency and cache-line transfers: IRQ and CPU isolation, sched_ext policies, proxy execution — kernel and system work rather than JACK code.
  • An opt-in isolation mode. Done for the shims' streams: async endpoints (§13), the switch per family. Still open for any JACK client: one chosen by the user running a cycle behind, its outputs double-buffered by the server (PipeWire's node.async), at a period of latency.
  • What a late client's output should sound like. Repeat, silence or a short fade (PipeWire plays silence, and fades on link removal): a matter of taste, parked.

25Packaging and deployment

nspa/pkg/jackbus/PKGBUILD builds one package from the repository's main branch (or a local clone with NSPA_REPO) that replaces Arch's jack2 and jack2-dbus.

JackBus

The same 62 files at the same paths as jack2 + jack2-dbus, and JackBus's own beside them; docs and lib32 left out.

  • Version. pkgver() from git describe on the 1.9.22 tag, e.g. 1.9.22.r98.g3b031c4e: sorts after 1.9.22.
  • Provides. jack, jack2=1.9.22, jack2-dbus=1.9.22, libjack.so=0-64, libjacknet.so=0-64, libjackserver.so=0-64; every package depending on jack2 (Ardour, mpv, OBS, qjackctl, wineasio, lib32-jack2) stays satisfied.
  • Conflicts. jack, jack2, jack2-dbus; it replaces jack2dbus-nspa, its former name.
  • JackBus's own files. /usr/include/jack/jackbus.h among the headers, its functions in the same libjack.so.0; the examples jackbus_simple, jackbus_tone and jackbus_events in /usr/bin.
  • The shims (§13). /usr/lib/jackbus-pw/libpipewire-0.3.so.0 and /usr/bin/jackbus-pw; /usr/lib/jackbus-pa/ (the dispatcher libpulse.so.0 and libjackbus-pa.so), /usr/bin/jackbus-pa and /etc/ld.so.conf.d/jackbus-pa.conf; /usr/lib/alsa-lib/libasound_module_pcm_jackbus.so and /usr/share/alsa/alsa.conf.d/50-jackbus.conf, linked from /etc/alsa/conf.d. Built against this build's libjack; libpulse is a dependency (jackbus-pa links PulseAudio's libpulsecommon), libpipewire and libpulse are needed to build. Nothing changes for an application until it is run through a shim or the user's settings say so: with pulse unset, every program loading libpulse gets PulseAudio's own library through the dispatcher, as before. jackbus-pa links alsa-lib for the cards' mixers (a device's volume, §13).
  • At login (§14). /usr/lib/systemd/user/jackbus.service beside Arch's jack@.service: not enabled by the package; systemctl --user enable jackbus.service starts JackBus through jackdbus before the desktop, in place of an autostart entry (hide or remove one: beside the unit it does nothing, on its own it starts JackBus after the desktop).
  • Build. Arch's configure options (--classic --dbus --systemd-unit --autostart=none) without doxygen; makepkg's flags with LTO; Berkeley DB 5.3 found by the wscript, no patch.
  • Validated as packaged. The full suite against the extracted package's binaries (38/38 at r72); the jackdbus tests, detach and timings included, against r98: 14/14.

Installing on a running system

jackdbus is a long-lived daemon: replacing files on disk doesn't replace the running process.

  1. Keep a way backsudo pacman -Sw jack2 jack2-dbus puts Arch's packages in the cache.
  2. Installsudo pacman -U jackbus-*.pkg.tar.zst; pacman offers to replace jack2 and jack2-dbus (or jack2dbus-nspa, its former name).
  3. End the old daemonjack_control exit. stop isn't enough: the old daemon keeps 1.9.22's libjackserver mapped and can't load the new drivers (undefined symbol … IsCaptureChannelNeeded).
  4. StartAt login, jackbus.service once enabled; now, jack_control start; D-Bus launches the new /usr/bin/jackdbus. If PipeWire held the card, a second start clears a "device busy".
  5. Checkreadlink /proc/$(pgrep -x jackdbus)/exe shows no "(deleted)"; GetXruns / GetLoad / GetClientTimings over D-Bus; ~/.log/jack/jackdbus.log.
